# Webhooks — тестове завдання Senior Frontend Engineer (Smart Sender)

Вхід, список вебхуків із пагінацією та пошуком, редагування. React 19 + TypeScript (strict),
API — мок на MSW за контрактом із завдання.

## Запуск

```bash
npm install
npm run dev        # http://localhost:5173
npm test           # автотести сесії (Vitest + msw/node)
npm run typecheck  # tsc --noEmit, strict
npm run lint       # ESLint: typescript-eslint (type-aware) + react-hooks
npm run format     # Prettier
npm run build
```

CI (GitHub Actions, `.github/workflows/ci.yml`) на кожен push і PR запускає lint, перевірку
форматування, типи, тести й збірку.

**Тестові облікові дані:** `demo@smartsender.test` / `Password123!`
(також у підказці «Hint» на екрані входу). Невірний пароль → 422 з помилкою біля поля.

Сесія мока живе 30 секунд — достатньо почекати пів хвилини й перейти на іншу сторінку списку:
у вкладці Network видно `401 → POST /auth/token/rotate → повтор 200`.

## Структура

```
src/
  api/          ← мережевий шар, не знає про React
    client.ts       заголовки, CSRF, 401 → rotate → повтор, 419 → новий CSRF → повтор
    index.ts        типізовані виклики: auth.signIn / me / revoke, webhooks.list / get / update
    errors.ts       ApiError + розбір формату помилки
    fingerprint.ts  стабільний ідентифікатор пристрою
    types.ts        контракт API
  app/          роутер, QueryClient, Layout, RouteError (замість білого екрана при помилці рендера)
  auth/         AuthProvider (користувач, вхід, вихід), RequireAuth, LoginPage
  webhooks/     сторінки списку й редагування, React Query хуки, стан списку в URL
  forms/        422 → помилки біля полів (react-hook-form)
  mocks/        MSW: db.ts (стан у пам'яті), handlers.ts (правила контракту)
tests/session.test.ts
```

API-логіка → стан (React Query + AuthProvider) → UI. Компоненти не бачать `fetch`, заголовків
і статусів: вони отримують дані або `ApiError`.

## Ключові рішення

1. **Один спільний rotate (single-flight).** `client.ts` тримає проміс rotate, що виконується.
   Запити, які отримали 401 одночасно, чекають той самий проміс. Сам rotate йде з
   `retryOnUnauthorized: false`, тому не може запустити новий rotate.
2. **Лічильник ротацій (`sessionGeneration`).** Після кожного успішного rotate лічильник
   збільшується. Якщо запит пішов до rotate, а 401 отримав уже після нього, він не ротує вдруге,
   а просто повторюється. Без цього повільний запит запускав би зайвий rotate.
3. **Повтор — рівно один.** Після rotate другий 401 або помилка rotate → `onSessionExpired`:
   локальний вихід, очищення кешу React Query, екран входу з поясненням.
4. **CSRF.** `GET /csrf` перед першим запитом, включно з логіном (це POST). Паралельні запити чекають
   один і той самий `/csrf`. На 419 — новий токен і один повтор. `X-Requested-With` — на всіх запитах.
5. **Токени.** `device_session_token` живе лише в області видимості `signIn`: його одразу обмінюють
   на сесію, він ніде не зберігається. Токени сесії клієнт не бачить взагалі: мок тримає сесію
   у себе (аналог HttpOnly-cookie). У `localStorage` — лише `fingerprint` (32 hex, `crypto.getRandomValues`).
6. **URL — єдине джерело правди для списку.** `page` і `search` не копіюються в `useState`.
   Перезавантаження, «назад» / «вперед» і посилання працюють без синхронізації. Зміна сторінки
   додає запис в історію; введення пошуку (з debounce 300 мс) — замінює, щоб «назад» не йшов по
   буквах; новий пошук → сторінка 1. Сторінку, якої вже немає (`?page=9` при 3 сторінках),
   виправляємо на останню.
7. **Після перезавантаження.** Сесія лише в пам'яті → треба увійти знову (як дозволяє завдання),
   але `RequireAuth` пам'ятає повну адресу, і після входу параметри списку з URL застосовуються.
8. **Валідація — на сервері.** Формат URL перевіряє API, клієнт показує помилки 422 біля полів
   (`forms/serverErrors.ts`). Одне джерело правил, без розбіжностей між клієнтом і сервером.
9. **Тестованість.** `createApi({ baseUrl, storage })` — без глобальних залежностей. Тест збирає
   власний екземпляр із пам'яттю замість `localStorage` і рахує запити через події MSW.
10. **Вихід посеред запиту.** Якщо натиснути «Sign out», поки летить запит списку, той після revoke
    отримав би 401, спробував rotate (400) і показав би «Your session has ended» людині, яка вийшла сама.
    Тому вихід спершу викликає `client.endSession()`: запити поточної сесії скасовуються
    (`AbortController`), а сигнал про закінчення сесії приймається лише від запитів поточної сесії.
11. **Помилки.** Помилки даних обробляють самі сторінки (стани запитів). Помилка рендера —
    `errorElement` роутера з кнопкою перезавантаження замість білого екрана.

## Тест

`tests/session.test.ts`:

- **обов'язковий:** два паралельні запити отримують 401 → рівно один rotate → обидва повтори успішні;
- запит, що летить у момент виходу, скасовується й не повідомляє про закінчення сесії;
- помилка rotate завершує сесію, без нескінченних повторів;
- CSRF: токен береться один раз перед першим запитом; 419 → новий токен і один повтор;
- 422 перетворюється на помилки за полями.

Перевірено, що тести справді ловлять помилки: без single-flight падає обов'язковий тест,
без `endSession()` — тест виходу.

## Що зробив би далі

- E2E на Playwright: вхід → список → редагування → закінчення сесії в справжньому браузері.

  (зараз обробник ідемпотентний, тож на поведінку це не впливає).
- Доступність таблиці й пагінації (оголошення зміни сторінки для screen reader).
